## 0. 一句话现状

一个 Unity 6（URP）俯视角末日生存游戏的**可运行原型**：能走、有边界、斜俯视跟随相机、灰盒场景、昼夜光照循环、砍树采集。

**规模**：约 26 个手写 C# 文件，全部在 `Assembly-CSharp`（**没有任何 asmdef**）。

## 1. 最初的明确要求

用户（非专业开发者）提出的约束：

**当前阶段只做最低可玩原型**：可移动玩家、有边界的 3D 地图、斜俯视跟随相机、少量灰盒建筑/墙体/箱子/树。**不要**战斗、动画、美术资源、UI、背包、任务、联网。

**开发原则**：
- 优先简单、可运行、方便扩展，**不要过度架构**
- 不为"未来所有可能功能"提前做复杂系统
- 但**已经明确未来一定会需要**的功能，要从结构上避免写死

**明确预告的未来需求（8 条）**：
1. **多地图**：家园 / 野外 / 聚居地是不同地图，不要假设当前 Scene 是唯一地图
2. **输入与移动解耦**：不要写死 WASD，要求 `Input → MovementIntent → CharacterMovement` 结构，未来接手柄/移动摇杆/AI
3. **相机独立**：Camera 只跟随，不承担控制逻辑；高度/距离/俯角/FOV/平滑都要 Inspector 可调
4. **通用交互接口**：树/箱子/门/NPC/工作台都要能交互，预留 `IInteractable`（当时不实现具体功能）
5. **物品系统数据化**：物品用 ScriptableObject 管理，不写死在代码里
6. **多层建筑**：坐标不要只按 X/Z 设计，从一开始考虑 `GridPosition = X, Z, Floor`
7. **存档**：不要求实现，但要避免"以后难以存档"的设计；世界物体/建筑/角色状态不要完全依赖场景对象
8. **未来可能联机**：绝对不实现，但避免所有逻辑只能由"本地玩家输入"触发

**用户指定的参考结构**（但强调不要一次性全实现）：
```
Game
├── Player     ├── Input / Movement / Interaction
├── Camera
├── World      ├── Area / Boundary
├── Items      ├── ItemData / Inventory
├── Building   ├── Grid / Floor / BuildingPiece
└── Save
```

## 4. 核心设计决策（及理由）

### 4.1 输入与移动解耦 ✅
`MovementIntent`（纯结构体，无 MonoBehaviour 依赖）是唯一契约：
```csharp
public struct MovementIntent {
    public Vector3 Direction;        // 世界方向，长度即强度
    public float SpeedMultiplier;    // 摇杆推杆量/冲刺/受伤
    public bool HasFacingDirection;  public Vector3 FacingDirection;
    public bool InteractPressed;
    public bool HasAimScreenPosition; public Vector2 AimScreenPosition;
}
```
`PlayerController` 只消费意图、**不读任何输入**。换手柄/AI/网络只需换 `ICharacterInputSource` 实现。

### 4.2 交互接口 ✅
```csharp
public interface IInteractable {
    string ObjectId { get; }
    Vector3 WorldPosition { get; }
    string InteractionPrompt { get; }
    bool CanInteract(GameObject actor);
    InteractionResult Interact(GameObject actor);
}
```
入口是 `Interact(GameObject actor)` 而非"本地玩家按 E"，所以 AI/联机玩家可复用。
返回值是 `InteractionResult` 而非直接改状态，便于以后做校验/回滚/网络确认。

**已验证**：树（重复采集）和箱子（一次性搜刮）行为完全不同，探测器和输入层**零改动**。

### 4.3 物品数据化 ✅
`ItemDefinition`（SO）持有 id/名称/描述/堆叠上限/图标。代码中**没有任何物品字符串硬编码**。
`Inventory` 是**纯 C# 类**（非 MonoBehaviour），因此箱子/NPC/联机都能各持一份，存档只需序列化数组。

### 4.4 地图与边界 ✅
地图的尺寸/内收/层数/出生点在 `MapAreaDefinition`（SO）。
`AreaBounds`（挂在场景 `世界` 物体上）是"这个场景是哪张地图"的唯一入口。
边界裁剪用**位移接口** `ClampMove(current, delta, margin)` 而非直接改位置，以便和物理共存。

### 4.5 相机独立 ✅
`TopDownCameraRig` 只跟随，不读输入、不控制角色。
关键设计：俯仰角由 `atan2(高度−视线高度, 后撤距离)` 反算；构图偏移按**吊臂长度的比例**计算，
因此改角度不会破坏构图。视角方位可固定（默认）或跟随角色朝向。

### 4.6 时间系统 ✅
`TimeOfDaySystem` 只管时间，对外暴露 `Hour/DayNumber/Phase/IsNight` + 4 个事件
（`OnTimeChanged` / `OnHourChanged` / `OnPhaseChanged` / `OnNewDay`）。
光照/雾/天空/后期处理都**只读它**，玩法（未来入夜刷怪）也读它。存档只需 2 个数字。

### 4.7 存档预留（部分）✅
`WorldObjectId` 持有稳定字符串 ID（格式如 `prototype/tree/003`），**刻意不用 `GetInstanceID()` 或层级路径**。
灰盒对象已写入 ID。但**没有实现任何存档读写**。

### 4.8 多层建筑预留（仅字段）⚠️
`MapAreaDefinition` 有 `_floorCount` / `_lowestFloorIndex` 字段（当前恒为 1/0）。
代码注释中明确了 `Floor` 与 `Y` 是两件事，位置概念上应为 `(X, Z, Floor)`。
**但没有实现任何网格/楼层逻辑**，且 `AreaBounds.ClampMove` 只处理 X/Z。

## 5. 我认为不规范的地方（请重点审阅）

### 5.1 🔴 没有 asmdef，且已造成真实的编译故障
所有代码在一个程序集里。更严重的是：编辑器脚本放 `Editor/` 文件夹会被编入 `Assembly-CSharp-Editor`，
而**这个跨程序集引用在本工程上反复失败**（`Assembly-CSharp-Editor` 找不到 `Assembly-CSharp` 里的类型），
导致 Play 按钮被禁用、排查了 4~5 轮。

**现在的应对是"绕过"而不是"解决"**：
- 把 `GreyboxLevelBuilder.cs` 从 `Editor/` 挪到普通目录，用 `#if UNITY_EDITOR` 包裹
- 所有对项目类型的引用改成**全限定名**（`Game.World.GreyboxPrimitives.CreateBlock(...)`），放弃 `using`

**这是一种反模式**。正确做法应该是加 asmdef（`Game.Runtime` / `Game.Editor`）+ 引用关系正确。
需要判断：这是本机环境问题，还是工程本身真的有问题？

### 5.2 🔴 场景内容靠代码生成，而非 prefab
`GreyboxLevelBuilder` 是一个 ~490 行的命令式场景生成器，用 `GameObject.CreatePrimitive` + `AddComponent` 拼场景。
- **优点**：可重复、无手工操作、改布局只改代码
- **缺点**：不是 Unity 的惯用做法。没有 prefab = 无法在 Inspector 里可视化调整，无法做 prefab variant，
  加载性能也无法优化。而且**中文字符串字面量被当作对象名**（见 5.3）

### 5.3 🟠 用中文字符串名做对象查找
```csharp
GameObject.Find("玩家");  GameObject.Find("相机吊臂");  GameObject.Find("视线点");
```
用名字做查找键。有 `FindOrRename` 兜底（兼容旧英文名），但这本质上是**用字符串当 API**。
正确做法是通过引用传递或 `[SerializeField]` 注入。

### 5.4 🟠 到处用 `FindFirstObjectByType` 做依赖注入
`PlayerController` 找 `AreaBounds`、`TopDownCameraRig` 找 `PlayerController`、
`InteractionProbe` 找 `InteractableBase`（每帧全场景搜索！）、光照找 `TimeOfDaySystem`……
这些是**隐式的场景耦合**，没有编译期保证，多地图/多玩家场景下会立刻出问题。

`InteractionProbe` 每帧 `FindObjectsByType<InteractableBase>()` 是最严重的一处 ——
对象上千时必须改成空间查询。

### 5.5 🟠 全局静态状态（`RenderSettings` / `Lightmapping`）
`DayNightLightingController` 直接修改 `RenderSettings.skybox / fog / ambientMode / ambientLight`。
这些是**进程级全局状态**，没有保存/恢复机制。
多场景切换（未来多地图）时，A 地图的雾会污染 B 地图。

### 5.6 🟠 昼夜系统是一个隐式单例
`TimeOfDaySystem` 是挂在 `昼夜环境` 物体上的 MonoBehaviour，通过 `FindFirstObjectByType` 被找到。
未来多地图/多世界会有问题（谁的时间？）。

### 5.7 🟡 `#if UNITY_EDITOR` 散落在运行时文件里
`GreyboxLevelBuilder.cs`、`DayNightSceneTools.cs`、`GameItemTools.cs` 都是运行时程序集里的编辑器代码。
这是 5.1 的后果，不是设计选择。

### 5.8 🟡 遗留的空文件
- `Assets/Game/Camera/CameraScreenAligner.cs`（0 行）
- `Assets/Game/Editor/GreyboxLevelBuilder.cs`（0 行）
两个都是重构残留，应该删除（但会造成空 `Editor/` 目录）。

### 5.9 🟡 完全没有测试
没有 EditMode/PlayMode 测试，没有 asmdef 所以也无法方便地加。
所有验证都靠人工 Play + 读日志。

### 5.10 🟡 文档与实现有偏差
`README_原型说明.md` 写于早期，部分内容已过期（相机参数、目录结构）。
另有 `Assets/Game/.keep`（内容其实是目录说明）。

### 5.11 🟡 序列化状态陷阱（已踩 3 次）
`[SerializeField]` 的**运行时**字段会被存进场景。已造成：
- `_hour` 存成凌晨 5 点 → 每次开局是黑天
- 相机 `_height/_backDistance` 存成旧值 → 改了脚本默认值不生效

现在的应对是加显式开关（`_useStartHourOnPlay`）+ 让用户手动在 Inspector 填值。**治标不治本**。
